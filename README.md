# Hermes Agent plugins

Plugins for [Hermes Agent](https://github.com/hermes-agent), each installable on
its own straight from this repository. There is no repository-wide version and
nothing to clone: you point the Hermes CLI at a folder and it installs that
folder.

## Plugins

| Plugin | What it does | Version |
| --- | --- | --- |
| [gpu-monitor](gpu-monitor/README.md) | NVIDIA GPU utilization, VRAM, temperature and power in the desktop status bar, plus an in-session `/gpu` command | [0.3.0](gpu-monitor/CHANGELOG.md) |
| [open-config](open-config/README.md) | Status-bar, palette and keybind shortcuts that open `config.yaml` and `.env` in your OS default editor | [0.1.0](open-config/CHANGELOG.md) |

## Install

```bash
hermes plugins install h4rry94/hermes-agent-plugins/gpu-monitor --enable
```

```bash
hermes plugins install h4rry94/hermes-agent-plugins/open-config --enable
```

Two things to know before the chip or the buttons appear.

**Restart the gateway.** The Python half is loaded at gateway startup, so a
fresh install is not serving its API or its slash command until you restart.

**Enable the desktop half separately.** Hermes keeps one enablement gate per
runtime component, so `--enable` above switches on the agent half only. Open the
desktop app and enable the plugin in **Settings → Plugins**. Settings may list an
agent entry *and* a desktop entry for the same plugin; that is one installed
package with two runtime components, not a duplicate install.

Each plugin's README covers its settings, its requirements, and how to update or
remove it. For a reproducible install, pin the commit:

```bash
hermes plugins install h4rry94/hermes-agent-plugins/gpu-monitor --ref <40-char-sha> --enable
```

`--ref` takes a full 40-character SHA, not a tag. Every
[release](https://github.com/h4rry94/hermes-agent-plugins/releases) publishes the
SHA to use.

## How a plugin here is shaped

One package, two runtime components, one install:

- a **Python half** that runs inside Hermes CLI and gateway processes — it
  registers slash commands and, where a plugin needs one, serves an HTTP endpoint
  the desktop half reads;
- a **desktop half**, a `desktop/plugin.js` the desktop app loads at runtime,
  which may import only `@hermes/plugin-sdk`, `react` and `react/jsx-runtime`.

Both live in the same folder because `hermes plugins install` copies exactly one
folder, verbatim. That is also the constraint the repository is organised around:
**every top-level plugin folder is independently installable**, with no shared
parent-directory files and no imports across plugins. A plugin that needs a file
carries its own copy.

`desktop/plugin.js` is generated from `desktop/plugin.tsx` by `pnpm build` and
committed beside its source, so a machine without Node can still install the
plugin. It is never edited by hand; CI rebuilds it and fails the pull request if
the committed bundle is stale.

Python is stdlib-only in both plugins. Nothing here installs a dependency into
your Hermes environment.

## Contributing

Read [RELEASING.md](RELEASING.md) first. Two conventions there matter more than
the rest:

- **A commit subject is the changelog line an installing user reads.** Write it
  in their voice. `main` blocks force-pushes, so a subject cannot be reworded
  once it has landed.
- **A scope decides which changelog a line lands in.** Use the plugin folder
  name, or `repo` for work that belongs to no single plugin. CI rejects anything
  else.

Changelogs are generated by git-cliff and never hand-edited. Releases are per
plugin, tagged `<plugin>-vX.Y.Z`, and run locally rather than in CI — the checks
that prove a release works need the Hermes CLI and a real GPU.

[PLUGIN_MIGRATION_GUIDE.md](PLUGIN_MIGRATION_GUIDE.md) is the reference for
adding a plugin or porting an existing one.

Run the tests from the repository root:

```bash
python -m unittest discover -s tests
```

They live here rather than inside a plugin folder because that folder ships to
everyone who installs it.
